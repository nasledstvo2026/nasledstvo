# Бизнес-требования (BRD) — «Консультант по наследству»

**Продукт:** автоматизированный мониторинг новостей наследственного права для пользователя Лены
**Версия документа:** 1.0 (черновик на согласование)
**Дата:** 25.08.2026
**Автор:** senior business analyst (Лунтик)
**Метод:** реверс-инжиниринг действующего решения (без интервью с владельцем)
**Основание:** skill `lena-news-expert`, `knowledge/lena/*` (news-knowledge.md, rzd-knowledge.md, sources.json), cron-пайплайн (search/verify/html), `product-lena.html`, `openclaw.json` (bindings), `.github/workflows/deploy-pages.yml`

## 1. Резюме для руководства

«Консультант по наследству» — автоматизированная система мониторинга новостей и изменений законодательства по наследственному праву РФ для Лены (консультант для граждан). Система ежедневно без участия человека собирает новости из 14 проверенных источников, верифицирует их, формирует дайджест и публикует его на GitHub Pages с доставкой в Telegram.

Продукт состоит из:
1. **Новостной cron-пайплайн** — 3 изолированных агента (поиск → верификация → HTML-отчёт), запускаются ежедневно в 02:00 / 02:10 / 02:20 МСК.
2. **РЖД-подсистема** — 3 агента (сбор MOEX ISS → валидация → отчёт по облигации РЖД 1Р-37R), в текущий момент **отключена**.
3. **Чат-агент** — диалоговый доступ к данным дайджеста, описан, но на практике **отдельным агентом не привязан** (Лена попадает в `main`).

## 2. Бизнес-контекст и проблема

### 2.1 Контекст
Лена консультирует граждан по вопросам наследования (вклады, недвижимость, нотариат, налоги, СВО-льготы и пр.). Ей необходима актуальная картина изменений: новые законы, судебная практика, разъяснения регуляторов, правила банков и СФР.

### 2.2 Проблема (RCA-формулировка)
> **«Лена не получает своевременный и полный обзор изменений по наследственному праву (пропуски событий, нерегулярность, дубли), потому что ручной мониторинг 14+ разнородных источников не выполняется ежедневно и единообразно, что вызвано отсутствием автоматизированного сквозного процесса "сбор → проверка → публикация".»**

- **Симптом:** дайджест либо отсутствует, либо неполный/устаревший.
- **Барьер:** ручной сбор из 14 разнородных источников (RSS/HTML/sitemap) без единого реестра и без проверки качества.
- **Корневая причина:** нет автоматизированного и воспроизводимого конвейера.

## 5. Область применения (Scope)

**Входит (in scope):**
- Автоматический ежедневный сбор новостей по наследству из реестра `sources.json` (14 доменов).
- Верификация: актуальность (≤7 дней), доступность, отсев рекламы/стоп-слов, регион (ru/world).
- Генерация смыслового контента (суть + «для граждан»).
- Формирование HTML-дайджеста и публикация на GitHub Pages + доставка в Telegram Лене.
- Дедупликация (по URL, fuzzy-заголовкам, истории `lena-news-seen.md`).
- РЖД-подсистема (облигация 1Р-37R) — по факту отключена, но задокументирована.

**Не входит (out of scope):**
- Редактирование/авторская переработка новостей человеком (полная автоматизация).
- Платный поисковый API (SearXNG/XMLRiver — выведены из схемы; сбор автономный, по белым доменам).
- Обработка обратной связи Лены (реакций на новости) и персонализация ленты.
- Уведомления в реальном времени (push по мере появления новостей) — только ежедневный дайджест.

## 6. Действующая архитектура (as-is, справочно)

```
02:00  lena-search-agent  → lena-raw.json (≤15)          [сбор]
```

## 7. Функциональные требования (FR)

### 7.1 Новостной пайплайн

| ID | Требование | Детали |
|----|-----------|--------|
| FR-1.1 | Единый реестр источников | `sources.json` — единственный источник правды о доменах, типе сбора (rss/html/sitemap) и URL. Whitelist генерируется из ключей реестра. |
| FR-1.2 | Сбор по всем источникам | curl по всем 14 доменам с User-Agent; rg.ru — трёхуровневый sitemap; при ошибке/пустом ответе — перейти к следующему, не зависая. |
| FR-1.3 | Детерминированный фильтр (без LLM) | Python-этап: whitelist доменов → дедуп по `lena-news-seen.md` → дата ≤7 дней (нормализация «N часов/дней назад»→ISO) → пустые title из слага → тематический фильтр точными стемами (наследств/наследник/наследодател/наследован/наследуем/завещан/завещател/выморочн). |
| FR-1.4 | Финальный отбор (один LLM-вызов) | ≤15 новостей; отброс не-текущего года и сомнительных дат; дедуп по заголовку >80%; приоритет категорий: законы > суды > банки > СВО > нотариат > налоги > недвижимость > СФР > международное > разное. |
| FR-1.5 | Запись результата | `lena-raw.json` (массив `{title, date, url, source}`); при 0 результатах — пустой массив `[]`; дописывание новых строк в `lena-news-seen.md`. |
| FR-1.6 | Верификация | Для ≤10 новостей (с приоритетом категорий): `web_fetch` статьи → проверка даты ≤7 дней, доступности, отсутствия рекламы и стоп-слов. |
| FR-1.7 | Регион | Классификация каждой новости `region: ru` / `world`. |
| FR-1.8 | Смысловой контент | Генерация `essence` (суть, 2–3 предложения) и `for_citizens` (практический вывод 10–15 слов). |
| FR-1.9 | Важность | `importance: main` (законы, указы, решения ЦБ/Правительства/КС/ВС) / `short` (остальное). |
| FR-1.10 | Проверка НПА | Для `importance=main` + категория law — проверка статуса НПА через LegalMCP (при доступности). |
| FR-1.11 | Запись верификации | `lena-verified.json` — все записи (verified + rejected) с полями исходного raw + `essence, for_citizens, importance, region, verification, reject_reason, stale_source`. |
| FR-1.12 | Дедуп внутри батча | Совпадение заголовков >80% → оставить один по авторитетности: pravo.gov.ru > rg.ru > tass.ru > rbc.ru > kommersant.ru > vedomosti.ru > остальные. |
| FR-1.13 | Контроль свежести входных данных | Если `lena-raw.json` старше 30 минут — выставить `stale_source: true` (предупреждение, не блокирует обработку). |

- Тематический фильтр точными стемами (запрет стемы «наслед» → отсеивает «наследие»; запрет «умерш/вдов» → отсеивает некрологи).

## 11. Критерии приёмки

1. Дайджест публикуется на сайте и доставляется Лене ежедневно без ручного вмешательства (проверка: 3 идущих подряд дня).
2. В дайджесте ≤7 новостей, все — релевантные (наследственная тематика), без дублей, некрологов и «культурного наследия».
3. Каждая новость содержит источник и пометку «для граждан».
4. Пустой день корректно отображается сценарием FR-2.3 (без ошибок пайплайна).
5. Сбой источника не роняет пайплайн; после 2 неудач приходит алерт Кириллу.
6. Верификация не «утекает» в лишние вызовы модели (один LLM-отбор на этапе search, без web_fetch на нём).

## 12. Допущения и ограничения

- Базовые метрики «до автоматизации» в решении не задокументированы — BRD фиксирует только целевые значения (target); baseline к реверс-инжинирингу не применим.
- LegalMCP заявлен как опциональная интеграция («при доступности»); фактический статус сервиса в решении не отражён.
- Правообладатели/robots ряда источников могут ограничивать доступ (tass JS-челлендж, pravo.gov.ru — JS-only): сбор может давать неполноту по этим доменам.
- Релевантность определяется эвристикой (стемы) + одним LLM-проходом — возможны ложноположительные/ложноотрицательные срабатывания.

## 14. Расхождения между документацией и реализацией (реверс-инжиниринг)

Реверс-инжиниринг выявил расхождения между заявленной документацией (`product-lena.html`, SKILL.md, MEMORY.md) и фактической реализацией. По каждому зафиксировано целевое требование, выведенное из фактического состояния.

1. **Документация отстала от кода.** `product-lena.html` описывает search-этап через `web_search` и таймаут 600 c; фактический промпт использует автономный сбор через `sources.json` (curl) и таймаут 1500 c. → Требование: актуализировать `product-lena.html` (автономный сбор + таймаут 1500 c).
2. **Чат-агент не реализован как отдельный агент.** Binding для 254785028 отсутствует → Лена попадает в `main`. → Требование: обеспечить binding 254785028 → `lena-chat-agent` (read-only к shared-файлам).
3. **РЖД-подсистема отключена** (3 крона disabled), хотя описана в SKILL.md и rzd-knowledge.md. → Требование: восстановить cron-пайплайн (FR-4) либо зафиксировать вывод из эксплуатации.
4. **Legacy-код.** `scripts/collect-lena-news.py` («три эшелона») не используется текущим пайплайном. → Требование: вывести из эксплуатации (архив).
5. **Рассинхрон в памяти.** MEMORY.md указывает ветку `gh-pages`; фактически и в TOOLS.md — ветка `master` (workflow деплоит master → gh-pages). → Требование: актуализировать MEMORY.md (ветка `master`).
6. **LegalMCP** — статус интеграции не отражён (упоминается «если доступен»). → Требование: зафиксировать фактический статус интеграции.
