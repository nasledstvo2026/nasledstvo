# Аудит оптимальности конвейера «Мониторинг жалоб» (Катя) — 27.08.2026

Основание: запрос Кирилла «полный глубокий анализ оптимальности пайплайна крона Кати».
Данные: 128 прогонов из `cron_run_logs` (27.07–27.08.2026), файлы `agents/shared/katya-*.json`,
живые пробы источников с VPS, тарифы из `openclaw.json`. Ничего в конвейере не менялось —
это только диагностика.

Стоимость на 80% состоит из cache-read (например у search: input 1.26M, output 531k,
cache-read 47.3M токенов за месяц). Деньги — не проблема ($30/год). Проблема — результативность
и надёжность.

## 2. P0 — Катя получает пустые сводки в 87% случаев

Факт: из 23 успешных прогонов `katya-agent` содержательная сводка ушла **3 раза** (07.08, 12.08,
17.08), «Новых жалоб не обнаружено» — **20 раз**, ещё 14 прогонов упали.

Причина: промпт фильтрует `verified` **по дате публикации жалобы** («за сегодня»), а не по дате
обнаружения. Жалоба от 21.08, найденная 24.08, в сводку не попадёт никогда. Прямое подтверждение:
24.08 verify добавил 12 новых записей — Катя в тот день получила «жалоб нет».

Следствие: ежедневная доставка Кате почти не несёт информации, а деградация конвейера
(как потеря базы 27.07) по сводкам не видна — «пусто» выглядит нормой.

Что нужно: фильтр по факту новизны (URL, которого не было в базе/seen), а не по дате публикации.
`katya_merge.py` уже проставляет `addedAt` и знает список добавленных за прогон.

## 3. P0 — прогоны сериализуются, фиксированные окна ломают порядок

Изолированные прогоны одного агента идут по очереди. Из логов:

- 27.08: search 07:45:00 → 07:55:39, verify стартовал 07:55:41 (ждал), katya — 08:02:20;
- 25.08: search 07:45:00 → **08:01:17** (977 с), verify 08:01:19, katya **08:01:19** — одновременно
  с верификацией, то есть по вчерашним данным;
- 24.08: search до 07:58:02, **katya 08:00:46 отработал раньше verify 08:03:17** — сводка построена
  до верификации;
- `katya-agent`: 9 падений с `job execution timed out` (300 с) при медиане 124 с — он таймаутил,
  стоя в очереди за search/verify.

Окна 07:45 → 07:55 → 08:00 рассчитаны на search ≤ 10 мин. Фактически search > 8 мин в 6 прогонах,
максимум 16,3 мин. Запас 10/5 минут недостаточен.

Что нужно: разнести окна с реальным запасом (search 07:30, verify 08:00, katya 08:20, stats 08:40)
и добавить в katya/stats guard свежести (`generatedAt` старше N часов → писать «данные не
обновились», а не «жалоб нет»).

## 4. P1 — search-agent: 80% стоимости, половина источников мертва

Живые пробы 27.08 (curl с User-Agent, 12 с таймаут):

| Источник | Ответ | Годность |
|---|---|---|
| banki.ru лента отзывов | 200, 904 КБ, 25 ссылок/стр, даты в листинге есть | ✅ основной (73% базы) |
| pravoved.ru `/search/?q=наследство` | 200, 131 КБ, 48 упоминаний стема | ✅ детерминированный поиск |
| 9111.ru | **447** (бан IP) | ❌ выкинуть |
| otzovik.com | 200, но 24 КБ JS-заглушка | ❌ выкинуть |
| sravni.ru/novosti | **301** редирект | ❌ выкинуть |
| asn-news.ru | 200, 50 КБ, наследственных материалов не найдено | ⚠️ почти бесполезен |

Дополнительно установлено:

- **Поиск по banki.ru через URL невозможен**: `?search=наследство` игнорируется, AJAX-эндпоинт
  `/services/responses/list/ajax/` отдаёт 167 КБ без ссылок и без текста отзывов. Значит наследственные
  жалобы ищутся только перебором карточек — это и есть источник 5–16 минут и 47 М cache-токенов.
- **У banki.ru есть rate-limit**: тестовый пакет 78 запросов за 9 с → IP заблокирован,
  `http=000` держался более 75 с. Текущий промпт про троттлинг ничего не знает; часть «пустых»
  прогонов search, вероятно, объясняется именно этим (и мой тест 75 карточек с нулём находок
  тоже испорчен баном — считать его оценкой частоты нельзя).
- **Двойная работа**: search делает `web_fetch` 3–5 лучших, verify затем открывает все URL заново.
- **Повторная верификация уже известного**: в прогоне 27.08 все 6 URL из `katya-raw.json` уже были
  в базе (дедуп по seen добавлен только сегодня).

Продуктивность: за последние 7 дней — 2 новые жалобы, за 14 — 12, за 30 — 36.
Цена находки: ~$0.09–0.28.

## 5. P2 — наблюдаемость и защита от тихой деградации

- `failureAlert` ловит только ошибки прогонов. Нет алертов на: «0 находок N дней подряд»,
  «база не выросла за неделю», «баланс провайдера на нуле». 26.08 весь конвейер лёг на billing
  error — узнали постфактум.
- Нет резервного запуска (ТЗ NFR-01 требует, фактически отсутствует).
- Счётчики конверсии (собрано → после фильтра → новых) нигде не сохраняются: историю
  продуктивности приходится реконструировать из текстовых summary.
- `stats-agent` бегает ежедневно, включая выходные, когда сбора нет — 8–9 прогонов в месяц
  пересобирают тот же HTML и коммитят в git (плюс: сейчас он же служит страховкой merge).
- HTML статистики каждый день рисуется LLM с нуля (452 k output-токенов/мес) — источник дрейфа
  вёрстки и формулировок; ровно так в отчёт и попало «Всего за неделю» вместо накопительной базы.

## 6. P2 — избыточные права кронов

У всех четырёх кронов в `toolsAllow` 23 инструмента, включая `cron` (крон может переписать
собственное расписание), `sessions_spawn`, `sessions_send`, `skill_workshop`, `create_goal`.
Фактически нужно: search — exec/read/write/web_fetch; verify — read/write/web_fetch/exec;
katya — read (+доставка); stats — read/write/exec. Это и риск, и лишний системный промпт
в каждом шаге агента (то есть тот самый cache-read).

## 8. Рассогласование временных окон

search собирает «за 7 дней» → verify верифицирует всё, что пришло → katya фильтрует «за сегодня»
→ stats считает «вся база + окно 7 дней». Четыре звена — четыре разных окна, из-за чего находки
теряются между звеньями (см. P0).

## 9. Что работает хорошо (не ломать)

- `katya_merge.py`: append-only, дедуп, бэкапы, guard, идемпотентность — база больше не может
  молча обрезаться (21 тест).
- seen-лист автоматически пополняется → повторный сбор одного и того же отсекается детерминированно.
- Расписание попадает в off-peak DeepSeek; стоимость $2.5/мес при 128 прогонах.
- `failureAlert` (after=2, cooldown 1 ч) на все четыре крона + дублирующий вызов merge в stats.
